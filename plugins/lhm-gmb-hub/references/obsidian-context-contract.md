# Obsidian-First Client Context Contract

Before every client-specific run, resolve the client in the configured Local Health Marketing Obsidian vault. Its canonical client, service and project records are the source of truth for identity, goals, targets, active work, decisions, constraints and run history.

Legacy references such as `client_profile.md`, `goals.md` and `current-projects.md` mean the matching record inside the resolved canonical Obsidian client root. Never create a same-named file in a repository, temporary workspace, plugin directory or delivery folder.

Read the relevant canonical service/project file and recent history before asking questions, analysing, proposing work or dispatching. BasicOps is live task state and Drive is a delivery destination; neither replaces Obsidian context. If a canonical record or field is missing, name the exact gap and route its addition through the owning Project Hub workflow. Do not create blank templates or parallel context. Only an authorised owning workflow may create or materially restructure canonical client records.

Do not infer the client root from a similar folder name. After authorised work, return durable state, decisions, evidence references, next executable stage and owner to the appropriate canonical Obsidian service/project file, preserving provenance.
