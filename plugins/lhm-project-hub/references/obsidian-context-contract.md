# Obsidian-First Client Context Contract

Before every client-specific run, resolve the client in the configured Local Health Marketing Obsidian vault. Its canonical client, service and project records are the source of truth for identity, goals, targets, active work, decisions, constraints and run history.

Legacy references such as `client_profile.md`, `goals.md` and `current-projects.md` mean the matching record inside the resolved canonical Obsidian client root. Never create a same-named file in a repository, temporary workspace, plugin directory or delivery folder.

Read relevant canonical context and recent history before asking questions, planning, creating BasicOps work or dispatching. BasicOps holds live task state and Drive holds material deliverables; neither replaces Obsidian context. If context is missing, name the exact gap and route creation or restructuring through the specific authorised Project Hub onboarding, kickoff, project-manager or client-update workflow that owns the record. A specialist or generic preamble must not create a blank template.

After authorised work, record durable state, decisions, evidence references, next executable stage and owner in the appropriate canonical Obsidian service/project file. Preserve provenance and avoid duplicating full Drive reports or BasicOps discussions.
