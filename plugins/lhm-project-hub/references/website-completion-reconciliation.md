# Explicit website completion reconciliation

Use for a current authenticated LHM team member's explicit “completed … reconcile/update the project” request, including a Lily BasicOps task-discussion mention. This is ordinary scoped record maintenance, not permission to launch, publish, approve copy or contact a client. Do not route this request into production dispatch.

1. Read the triggering task and its complete Discussion/replies, resolve the client, and read shared `client_profile.md`, `Current Projects.md` and the canonical website note. Resolve the note from the existing overview link or Current Projects detail pointer first. Otherwise inspect `project-management/` for the existing Website Rebuild, Website Redevelopment, Website Build, Website and Landing Pages or website note. Read the candidate before choosing. A draft/workflow template is not a second canonical note. Multiple plausible notes require clarification; missing notes require a scoped creation/recovery decision, never silently write a duplicate. All `website.md` examples mean the resolved existing path.
2. Match the update to specific checkbox IDs or unique task text. Preserve phase structure, owners, dependencies, dates and history. A broad “content finished” does not complete reviews, implementation, QA, approval or launch. Ambiguous matches stay open; ask the one question needed. Capture the completion statement's author/date and supplied evidence link; distinguish self-reported completion from independent verification. Approval needs its own named approver, source, date and version.
3. Record only the supported items as complete, with date and evidence. Preserve pending approvals and unrelated work. Add a dated reconciliation entry with the source task/discussion link and actor. Read the saved file back and compare the exact changed items. A failed write blocks dependent state changes; never claim success. If Obsidian succeeded but BasicOps failed, report partial success with the durable note path, and retry only the failed operation after fresh reads.
4. Determine the immediate next action by dependencies and approval gates, not the first unticked box. Align the website block in Current Projects. Through `basicops-task-manager`, update only the exact task/owner/stage authorised by the request and verified context. Finishing one checklist item does not complete an entire overview. Keep personal weekly commitments unchanged. Prepare a handoff when a new action/owner is clear; creation still follows the existing task authority rules.
5. Read back Obsidian and any changed BasicOps record. Reply in the triggering thread with: exact completed items and note link/path; BasicOps changes or none; items/approvals still open; next owner/action; any blocked write. Include before/after state for changed task fields. Use the triggering message ID as the reconciliation key; before retry, inspect the log and live state. Reuse existing completion/history entries and replies instead of duplicating them. Never mark the event done until the readback result or explicit partial failure has been returned.

Website content batches return a handback containing page IDs/URLs, approved versus produced status, review evidence, remaining work and next owner. Reconcile this against the same canonical note; repository batch trackers alone do not satisfy the project handback.

## Hermes shared-vault writer

Do not assume `/opt/data/profiles/lhm_brain/vault-lhm-knowledge` is synchronized. For Hermes, use the installed Loops writer and the verified shared-Drive mapping in `/opt/data/profiles/lhm_project_manager/website-loop.json`. The `website-project-loop/scripts/website_loop.py complete` command takes `--task`, `--item` (unique existing checkbox text/ID), `--date`, `--evidence`, `--source` (triggering discussion URL) and `--actor` (verified reporting person). It reads the actual shared profile/checklist and current discussion, writes only the exact production checkbox, records attribution and reads back the saved shared file. It refuses approval, merge, deployment or launch gates. The agent must first verify that the authenticated request supports that item and evidence. This helper does not update BasicOps or return the thread response: perform those through the owning task-manager and verify them separately. Missing mapping blocks the helper; resolve/register the existing note before retrying, never write to a stale local mirror as a substitute.

Claude with a directly mounted synchronized shared vault can use its normal file tools under the same read/write/readback contract; the Hermes helper is not a prerequisite for manual Claude use.
