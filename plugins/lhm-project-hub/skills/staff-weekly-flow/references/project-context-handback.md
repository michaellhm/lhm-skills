# Incremental project-context and task handback

## Apply each settled item

1. Resolve the verified shared client root under the client knowledge routing contract. Read its
   overview/profile, Goals.md, Current Projects.md and affected project notes before changing facts.
   Preserve newer correct state from other sessions; reconcile dated conflicts rather than replacing
   it with this session's earlier report.
2. Save clear authorised project feedback immediately after the item is settled, without waiting
   for the whole weekly plan or asking a redundant generic save question. Update only affected
   canonical facts: decision/status, scope, blocker, owner, next action/checkpoint and source/date.
   Put detail in the existing project note and reconcile the Current Projects summary; assess other
   records as unchanged when no facts changed. Attribute reported completion and distinguish it from
   verified delivery, approval, publication or sending. A missing client root is a pending routing
   gap for the onboarding/client-update owner, not authority to create a replacement folder.
3. Assess the BasicOps consequence separately. Read the existing relevant shared cockpit/personal
   execution task and discussion; deduplicate before creation. Route only the exact authorised task,
   discussion or board change through basicops-task-manager. Reuse existing item-specific authority;
   ask only for genuinely missing authority. A context update alone does not authorise completion,
   reassignment, a new deadline, bulk staff-board moves or external notification. When a saved decision
   changes the task brief or handoff, include that bounded update in the routed operation rather than
   leaving execution instructions stale. Verify the task fields and any discussion after application.
4. Save the compact decision and links in the existing person/week and relevant shared portfolio
   note. These are continuity records, not the only home of project state. Keep private capacity,
   founder material and staff-private assessments outside shared client records.
5. Read back changed canonical records and task state. Record each destination as `updated and
   verified`, `unchanged — reason`, `pending authority`, or `blocked/failed — exact next step`.
   Never mark BasicOps updated because an Obsidian note exists, or client context updated because a
   weekly note/task exists. Deduplicate by source/item and re-read before retrying.

## Close and resume

Maintain a compact destination register in the existing weekly note: project/item, source/date,
canonical paths and result, BasicOps links and result, next owner and pending action. Link to
records rather than copying their full contents. Save settled items even when the remaining plan
is partial; resume from verified saved decisions without repeating the intake.

Before the Tuesday document or final wrap-up, reconcile every settled project mentioned against
this register. Fix authorised missing writes; carry unavailable destinations and missing authority
as explicit pending items. Reconcile current summaries when a draft is subsequently sent, a blocker
is resolved or newer evidence supersedes an earlier report, while preserving dated history. Return
actual destination links and coverage gaps; do not claim complete handback until all required writes
have been read back. Next run reads canonical client state plus the latest weekly decisions and live
BasicOps state, so another staff member can continue from the same evidence.

## Acceptance scenarios

- A project update is saved in the weekly portfolio only: canonical client handback remains pending;
  update the affected project note and Current Projects, read back and link them before closing.
- The user reports completion and a blocker: attribute both in canonical context immediately;
  assess exact task changes without closing the entire project or changing another person's board.
- An accepted task handoff changes the brief: reuse the existing task via task manager, apply the
  authorised brief/discussion and verify it; a note alone does not satisfy the execution handoff.
- A later session has already delivered work: preserve its dated evidence and reconcile this flow's
  earlier not-started report; do not overwrite the newer state.
- A draft is later sent: update the current canonical/weekly summary to verified sent, keep history.
- A write fails or the session is interrupted: retain exact pending destinations, resume with live
  read-back, skip already-applied updates and create no duplicate tasks, notes or comments.
- Missing client root or unapproved task mutation: record the gap/owner, finish independent writes
  and report partial coverage instead of inventing a record or claiming both systems are saved.
