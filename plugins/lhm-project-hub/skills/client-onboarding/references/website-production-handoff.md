# Website intake and production handoff

Use for a new website client after sales and strategy evidence is available. Client-specific names, prices, dates, platforms and page counts come from that client's sources, never from another client's example.

## Intake, evidence and gates

1. Read existing client overview/profile, Goals, Current Projects, handover, Onboarding, website project and live BasicOps discussions. Verify separate knowledge and work destinations using the shared routing contract.
2. Resolve the commercial route: direct LHM or partner/Marlon. Record payment receipt from explicit human confirmation or provider evidence with its verification method. Ask only when unclear; never infer payment merely from a Fathom title or intention to pay.
3. Store a separate sourced record for the sales call and the strategy/onboarding call. Capture commitments, questionnaire answers, client voice, scope, booking journey, services, approvers, assets and deferred work. If a user supplies the transcript, use it even if connector searches missed the recording. Never claim recording playback from a pasted transcript.
4. Reconcile meeting record, overview/profile, goals, current projects and affected service note. Preserve address/name conflicts, provisional page counts, rejected wording and unapproved claims. Client anecdotes and clinical beliefs are discovery evidence, not automatically public testimonials, medical facts or outcome guarantees.
5. Create/link the handover and canonical project brief. The full campaign master is a production deliverable; do not repeat a completed strategy interview because that document remains unwritten. Clear contact/strategy only against the required evidence or a recorded explicit human exception.

## Communications and BasicOps review

Prepare both communications as part of handover, not an optional final offer:

- Internal email to the verified coordinator and salesperson/partner, with additional team recipients only in authorised scope. Introduce the client, practitioner/business, location and website URL; state purchased work, payment/contact/strategy state, immediate actions, owners and links. Keep it short. Do not assign client sign-off or add retained-approval prose unless actually requested.
- Client email introducing the coordinator, what happens next, representative prototype and feedback sequence, requested media/permissions/details/access and confirmed timing. Explain tracking in client terms: understand discovery and booking performance. Introduce the technical specialist when relevant. No passwords, fabricated setup or unapproved commitments.

Show editable writing blocks where supported and preserve the latest manual edits. Draft-ready, user-approved, sent and provider-verified are separate states. Read sent history before retrying an uncertain send. If the user says review first, show concrete drafts and proposed tasks before any send, creation, reassignment, completion or move. Sending one email does not approve another. Do not describe a timeout or interrupted request as unsent without checking.

Use basicops-task-manager for all mutations. Show coordinator access/assets work, specialist tracking/configuration work and the website lead's campaign/prototype task together for review when requested. Reuse the seven existing gates and the website overview/personal execution task; do not create a second onboarding tree or one task per page. Preserve linked tasks when authorised moves place them on personal boards. Resolve actual boards/sections, then verify native IDs, owners, status, due dates, discussions and parent links. Do not infer task dates from vague timing or treat client emails as implementation evidence.

For purchased website measurement, coordinator obtains required GBP/platform access and media/practical details; verified specialist owns GA4/GTM/GSC, agreed conversions, appropriate client ownership access and testing. If Nookal or another booking platform is involved, inspect current supported installation/measurement route, then prepare instructions and verify the real boundary. Never assume completed bookings are trackable from a parent-page click. Ask only for scope-relevant accounts; don't impose this branch on every client.

## Portable execution prompt

Prepare one self-contained prompt for the website lead (prototype-lead where installed). Preparing it does not dispatch an agent or create a chat. Include:

- Concrete outcome, task URL/ID, owner, latest status, authorised target and source freshness.
- Canonical record paths, sales and strategy sources, verified work-folder link, existing sitemap/brand/prototype references and concise evidence summary. If the executor lacks access, identify exact material to request rather than assume inherited chat/connectors.
- Confirmed objectives, audience, positioning/voice, services, booking journey, practical facts, approval path, unresolved conflicts, exclusions and dependencies owned by others.
- Three ordered deliverables below, skill availability, required checks, actual authority and precise handback.

### 1. Campaign master document

Read any existing campaign/playbook owner and template first; use `lhm-marketing-hub:playbook-strategy-session` for supported strategy context without rerunning discovery. If no exact campaign-master producer is installed, state partial coverage and use a bounded sourced synthesis instead of inventing a slash command.

Cover objectives/success measures, audience needs/objections, positioning, voice, confirmed services/locations, architecture, recommended prototype pages, page purposes/messages/CTAs, booking journey, asset/measurement dependencies and decisions versus recommendations. No invented targets or claims. Get material scope decisions reviewed before committing them to final copy.

### 2. Documented design system — UI UX Pro Max required

Require the installed UI UX Pro Max plugin/skill and read its actual instructions. If unavailable, report the gap; never claim use. This task-specific requirement overrides homepage-prototype's optional-helper wording. Use the client's actual brand/assets and audience brief; do not blindly accept generated design suggestions that conflict with those constraints.

Save reusable colour/contrast, typography, spacing, layout/breakpoints, buttons/links/forms/navigation, component/states, imagery and keyboard/focus rules with audience rationale. Build the prototype consistently from the documented system.

### 3. Representative prototype

Use `lhm-marketing-hub:homepage-prototype` for supported homepage/design/QA work; use the installed website owner for the additional representative pages. State partial coverage where the homepage skill does not cover multi-page production. Select the evidenced number of pages and explain their purpose; never default every client to five–six or a particular full-build count.

Create coherent navigation and substantive client-specific draft copy. Reuse existing sitemap, brand and approved work. Verify booking destinations without submitting bookings or inventing integrations. Flag unresolved facts and assets visibly before public use. Client prototype approval precedes full build.

## Acceptance and handback

Save campaign master, design system and prototype in the verified work folder with existing service conventions. Update canonical knowledge with concise evidenced decisions and links, not duplicate deliverables. Verify real mobile/desktop screenshots, overflow, keyboard/menu behaviour, contrast/focus, images, links, copy accuracy and design-system consistency.

Return deliverable links, UI UX Pro Max evidence, checks passed/incomplete, blockers, decisions requiring review and exact next owner/action. No sending, BasicOps mutation, permission change, live tracking change, GBP creation, publication or deployment follows merely from the prompt; carry only actual authority granted. Readback precedes any completion claim. Distinguish local, saved, reviewed, published and launched.

End the execution prompt with:

“When the session finishes, run `/learn` (`lhm-learn:learn`) if installed. Capture verified client facts in their canonical records and reusable methods, corrections and skill gaps with evidence. Prefer improving the existing owning skill; propose a new skill only for an evidenced uncovered workflow. Apply only already authorised source changes; merge/install need separate authority. If Learn is unavailable, return a concise learning handback for the coordinator.”

## Review cases

- Partner payment confirmed: no duplicate collection; record human versus provider evidence.
- Sales and strategy transcripts supplied: capture separately, reuse questionnaire, no repeat interview.
- Draft edited then approved: exact latest text/recipients, verify SENT; other email remains held.
- Review-first request: no tasks created or sent before approval; uncertain sends checked before retry.
- UI UX Pro Max missing: capability gap, no false compliance claim.
- Campaign document unfinished: production remains open; no fabricated whole-onboarding completion.
- Personal-board moves approved: preserve original IDs/parent links, verify destination and owner.
- Prototype approved: full build still requires its own scope and publishing/launch boundaries.
