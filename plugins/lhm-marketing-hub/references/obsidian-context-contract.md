# Obsidian-First Client Context Contract

This contract applies before every client-specific skill or agent run.

1. Resolve the client in the configured Local Health Marketing Obsidian vault first. The canonical client root and its service/project records are the source of truth for identity, goals, commercial targets, active work, decisions, constraints and run history.
2. Legacy names such as `client_profile.md`, `goals.md` and `current-projects.md` mean the matching canonical record inside that resolved Obsidian client root. They never authorise creating a same-named file in the current repository, a temporary workspace, a plugin directory or a delivery folder.
3. Read the relevant service/project file and recent history before asking questions, analysing performance, proposing work or dispatching another agent. Use BasicOps for live task state and Drive or the governed delivery destination for material deliverables; neither replaces Obsidian context.
4. Do not create blank templates or parallel context files when a canonical record is missing, unavailable or incomplete. State the exact missing field or record, preserve any evidence already found, and route the context addition through the owning Project Hub workflow. Only that authorised workflow may create or materially restructure canonical client records.
5. Never infer that a local folder is the client root merely because its name resembles the client. If the canonical Obsidian client cannot be resolved unambiguously, stop client-specific writes and request resolution.
6. After authorised work, return durable state, decisions, evidence references, next executable stage and owner to the appropriate canonical Obsidian service/project file. Preserve provenance and do not copy an entire Drive report or BasicOps discussion into Obsidian.

Before substantive work, retain or report the resolved client/root, records read, exact context gaps, live task-state source, delivery destination and approval state when relevant. A context gap may lower confidence or block a dependent decision, but it does not permit a blank replacement file.
